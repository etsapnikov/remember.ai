## Дизайнеру

### Диз-1 · Состояния клавиши записи: idle / запись / стоп кнопкой

Контекст. Сейчас экран записи всегда «пишет»: иконка открывает приложение сразу в
запись (capture-first, это не обсуждается), стоп — тап по любому месту экрана.
Владелец: тап по пустому месту не читается как действие, нужна **явная кнопка
«завершить запись» — и обыграть её большой красной клавишей в центре**. Плюс
появилось новое состояние: после возврата из ленты запись уже не идёт (решение
Р-9), и клавиша впервые оказывается в состоянии «не пишу».

Задача. Спроектировать три состояния клавиши (`ui/components/RecordKey.kt`,
геометрия из токенов `key`: корпус 112, колпачок 84, нажатый 78, точка 26):

1. **Запись идёт**: клавиша = кнопка «стоп». Как выглядит нажатие (глубина, ход
   колпачка), что происходит с пульсом. Тап по экрану вне клавиши — решить: тоже
   стоп (как сейчас) или только клавиша.
2. **Idle** (вернулись из ленты / после отмены): клавиша = кнопка «начать». Чем
   idle отличается от записи визуально, кроме отсутствия пульса — человек должен
   с одного взгляда понимать, пишет сейчас телефон или нет.
3. **Переход idle → запись** по нажатию: моушн в терминах токенов `motion`.

Ограничения айдентики (§4): без микрофонов, волн-эквалайзеров и подписей на
клавише. Аффорданс «на неё хочется нажать» — главный критерий.

Приёмка: человек вне команды по скриншоту отвечает, идёт ли запись; и говорит,
куда нажать, чтобы остановить/начать.

### Диз-2 · Таймер и живая индикация записи

Контекст. Владелец: «таймер невнятный — маленький и непонятный», «не понятно,
пишется ли речь». Сейчас: JetBrains Mono 30sp над клавишей + пульс-кольцо вокруг
неё, амплитуда голоса уже прокинута в UI (поле `level` 0..1 обновляется каждые
100 мс — можно использовать сразу).

Задача: спроектировать индикацию «я тебя слышу» без клише волны-эквалайзера
(запрет айдентики §4). Направления на выбор, не ограничиваться: дыхание самой
клавиши от громкости; кольцо-пульс с амплитудой; наливающаяся точка. Таймер:
размер/место/поведение (возможно, он вторичен и растворяется, пока идёт речь, и
проявляется в тишине — решить). Отдельно: как выглядит тишина (человек замолчал,
через 2 с будет авто-стоп) — это стоит показать, сейчас авто-стоп «внезапный».

Моушн-спека в терминах токенов. Помнить бюджет: индикация обновляется от
`maxAmplitude` раз в 100 мс, интерполяцию между тиками задать явно.

### Диз-3 · Ребрендинг: «Запомин.ai», квитанция «Запомнил.»

Решение владельца 07.08.2026: имя приложения — **Запомин.ai**, квитанция —
**«Запомнил.»** (вместо «Принял.»).

Честное предупреждение, которое надо отработать, а не проигнорировать: айдентика
строилась на правиле «имя продукта = его реплика» (ТЗ айдентики §2). Пара
«Запомин.ai / Запомнил.» это правило сохраняет почти целиком — но леттеринг
квитанции, вибро-паттерн и иконка проектировались под слово из шести букв с
точкой. Проверить: как «Запомнил.» ложится в кегль display 38 на узких экранах;
не ломается ли ритм точки; нужно ли трогать иконку (владелец не просил — по
умолчанию не трогать).

Deliverables: выверенная квитанция «Запомнил.» (кегль/трекинг, если нужен —
правкой токенов), правило написания имени в сторах и в тексте («Запомин.ai», где
точка, где регистр), ревизия строк словаря, где встречается «принял».

## Разработчику

### Р-К (критикал, вместе с Р-9) · Запись-зомби после свайпа в ленту

Репро владельца: свайп вверх во время записи → работа с заметками → возврат на
экран записи: таймер показывает 1:30 и новая запись не начинается; остановить
нельзя, лечится только перезапуском приложения.

Разбор: 1:30 — это потолок `Recorder.MAX_DURATION_MS` (90 с). Пока лента открыта,
запись продолжается (так велела спека R1.1 §7), на потолке `finishRecording()`
срабатывает в «тихом» режиме (`feedOpen == true`): заметка сохраняется, но
`state.elapsedMs` остаётся 1:30, а `beginRecording()` вызывается только в
`onCreate` — экран записи после возврата мёртв. Файлы:
`capture/CaptureActivity.kt` (`finishRecording`, `feedOpen`),
`capture/CaptureHost.kt`.

Решение — вместе с Р-9 (владелец отменил «запись продолжается при открытой
ленте»): **свайп вверх завершает запись** (сохранить, если ≥ 1.5 с; иначе тихо
отменить), лента открывается уже без записи, баннер «Идёт запись» удаляется.
Возврат на экран записи ведёт в **idle-состояние** (см. Диз-1): клавиша
запускает новую запись по нажатию, таймер обнулён. Запуск с иконки/виджета
по-прежнему стартует запись сразу — capture-first не трогаем.

Приёмка: свайп вверх во время записи → заметка в ленте со статусом; возврат →
idle, тап по клавише → новая запись с 0:00; сценарий «свайп → 5 минут в ленте →
возврат» не оставляет ни зомби-таймера, ни битого файла.

### Р-8 (критикал) · Возвраты не доходят: прошивка убивает приложение

Факт: за два дня не пришло **ни одно** уведомление возврата (риск PRD §9
подтверждён). Телефон — Honor Magic6 Pro (BVL-AN16, Android 16, логкат
зашифрован). Алармы ставятся через `setExactAndAllowWhileIdle`
(`returns/ReturnScheduler.kt`), `drift_ms` пишется в analytics при срабатывании —
записей о срабатываниях нет вовсе: ресивер не просыпается.

Сделать, в порядке дешевизны:
1. **Диагностика на устройстве**: `adb shell dumpsys alarm | grep prinyal` после
   постановки — стоит ли аларм в системе; `cmd appops get ai.prinim.prinyal.debug`
   и hwaudit-каналы Honor. Зафиксировать, теряется аларм или блокируется старт
   процесса.
2. **Батарейные исключения**: запрос
   `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` + на Honor/Huawei отдельно
   «автозапуск» (protected apps) — интент на их настройки, экран-подводка в тоне
   §4.1 («без этого не смогу напомнить»). Показать один раз из настроек, секция
   «Система».
3. **Страховка WorkManager'ом**: периодический (15 мин, `PeriodicWorkRequest`)
   `ReturnCatchUpWorker`: выбирает `returns.due(now)` и показывает пропущенные —
   петля с люфтом лучше молчащей. `drift_ms` честно покажет деградацию.
4. Если и это душится — foreground-сервис на время ближайшего окна (см. PRD §9
   «foreground-fallback») — только после замера, не сразу.

Приёмка: возврат приходит при убитом из recents приложении и после суток простоя;
`return_fired` появляется в analytics с drift < 15 мин (цель §8 в 2 мин — после
пп. 1–2, замерить фактический drift страховки).

### Р-3 · Значок уведомления в статус-баре не виден

Репро: уведомление приходит (разбор), но значка в трее нет. Маленькая иконка —
`res/drawable-nodpi/ic_notification.png` (белый PNG 96px из ТЗ айдентики). На
проверку: Android требует альфа-маску — белый непрозрачный квадрат станет белым
квадратом, а белое-на-белом или неверная альфа = невидимость; плюс nodpi-PNG на
плотных экранах мылится.

Сделать: перевести small icon на **VectorDrawable** (монохром, только альфа) по
глифу нотификации из айдентики; проверить в шторке светлой и тёмной темы и в
статус-баре; заодно убедиться, что цвет бейджа берётся из `accent_self`
(`returns/Notifications.kt`, `setColor` уже стоит). Приёмка — тест айдентики §9.2:
значок находится в статус-баре с первого взгляда.

### Р-4 · Умный момент возврата (проактивный харнес, первый шаг)

Боль: возвраты привязаны к фиксированному времени окна; хочется «в правильный
момент». Полный харнес (гео, контекст) — R2 по PRD, но есть дешёвый первый шаг:

**Доставлять возврат в момент, когда человек взял телефон** внутри окна, а не по
будильнику. Механика: аларм на начало окна взводит «armed»-состояние; показ — по
`ACTION_USER_PRESENT` (разблокировка) в пределах окна `[start, start+90 мин]`;
если разблокировок не было — показать по концу окна как сейчас. Это же смягчает
Р-8: разблокировка — момент, когда процессу точно дают жить.

Данные для тюнинга уже есть: `analytics.jsonl` пишет `return_fired`/`return_action`
— доля ответов «в течение минуты после показа» покажет, попали ли в момент.
Реализация: `returns/` + ресивер USER_PRESENT (регистрируется динамически, пока
жив процесс — ещё один аргумент за страховочный воркер из Р-8).

### Р-6 · Вау-разбор трёх живых сценариев (промпт-тюнинг на корпусе владельца)

Владелец надиктовал корпус: списки дел/покупок, брейншторм, поиск информации.
Корпус лежит прямо в телефоне: `files/analytics.jsonl` + таблица `notes`
(транскрипты) — вытащить `adb shell run-as ai.prinim.prinyal.debug`.

Задача: прогнать корпус через текущий промпт (`llm/Prompt.kt`, версия 2; зеркало —
`backend/app/prompt.py`) и довести разбор до «вау» на этих трёх типах:

- **списки покупок/дел**: дробление на отдельные buy/do пункты без потери
  позиций, «и молоко и хлеб» ≠ один пункт;
- **брейншторм**: не дробить в фарш — крупные мысли (`thought`) с сохранением
  формулировок владельца; возможно, новое правило в промпт «поток идей об одном —
  один пункт с под-строками»;
- **поиск информации**: «посмотреть/загуглить/узнать» → отдельная семантика
  (сейчас размазывается между do/thought). Кандидат: `type=lookup` — НО новые
  типы требуют владельца: тип попадает в БД, глифы-чипы и метрики. Согласовать до
  реализации, дешёвая альтернатива — do + who=null + маркер в тексте.

Формат работы: eval-набор из корпуса (вход → ожидаемые пункты), гонять промпт-
варианты через `backend/scripts/` (есть venv с httpx), метрика — ручная разметка
владельцем «вау/ок/мимо» по 10–20 записям. Версию промпта поднять синхронно в
обоих местах (тест `промпт на устройстве той же версии, что на сервере` уже есть).

### И-7 · Web search в API DeepSeek

Вопрос: есть ли у DeepSeek API серверный веб-поиск — тогда разблокируются
сценарии факт-чека и «найди мне» для харнеса.

встроенного server-side web search **не было** — поиск в их продуктах жил в
приложении, не в API; в API есть function calling. План проверки: (1) docs
platform.deepseek.com — разделы tools/search; (2) если нет — прототип: function
calling + внешний поиск (Tavily/Brave/SearchAPI, у всех бесплатные квоты) —
день работы, тогда «посмотреть что за фильм» превращается в возврат с готовым
ответом. Оценить стоимость на запись и латентность против бюджета 6 с §8.
Выход: страница в docs/ с вердиктом и, если «да», — списком сценариев харнеса
по приоритету владельца.
